# 10 万人同时在线：容量规划与部署

这份文档回答三个问题：10 万人在线时哪里会先撑不住、架构怎么解决、要多少机器（以及怎么在上线前验证）。

> **诚实说明**：10 万个真实连接无法在开发用的单台 4 核机器上跑出来。下面的数字分两类：**实测**（在 4 核机器上的缩比实验，标注“实测”）和**推算**（由实测的单位成本乘出来，标注“推算”）。正式上线前请用文末的分布式压测流程在你的真实机器上复核。

## 1. 10 万人时的瓶颈，以及对应的设计

| 瓶颈 | 不处理会怎样（推算） | 现在的做法 |
|---|---|---|
| **下行带宽**（最大的成本） | 10 万人 × 20 KB/s = 2 GB/s ≈ 16 Gbit/s | 只发视野内的区块、编码一次扇出、差量 + 量化，缩小时自动切 2.5 Hz 低频档（每人省 43%）。见 benchmarks.md |
| **网关吞整个世界** | 玩家分散在世界各处时，每个网关上几千人的视野加起来覆盖全图：128×128 世界每个网关进程约 260 Mbit/s 内部流量，几十个网关合计约 9 Gbit/s | **分区（zones）**：世界切成若干区，每个区一组网关；玩家看哪个区就连哪个区，镜头跨区时客户端先连新区、填好画面再断旧连接，画面不中断。实测（2×2 区）每个网关内部流量降为 1/2.9，16 区时约 1/10 |
| **模拟算力** | 100 万个实体需要几十个核 | 世界分片 + 动态负载均衡（热点区块自动搬到空闲分片）+ 时间膨胀兜底 |
| **人群挤在同一处** | 一个区块被 10 万人操作、刷聊天 | 每区块每 tick 最多 20 次工具操作、32 个光标、64 条事件；聊天抄送后台按每分片每秒 100 条抽样；整个区的网关池可以单独扩容 |
| **控制面消息** | 每次搬区块要给上百个进程各发一张 50 KB 的完整地图；进人高峰时注册消息数量成倍放大 | 地图只发增量（掉了版本的进程会主动要完整地图）；玩家注册每 50 ms 批量发一次；世界概览降采样到最多 48×48 格，缩小时每 2 秒发一次，其他情况每 6 秒发一次 |
| **入口负载均衡 / TLS** | 单个 Caddy 撑不住 16 Gbit/s | 前面用云厂商的四层负载均衡（或 DNS 轮询多台 Caddy / Cloudflare）。网关本身无状态，不需要粘性会话 |

## 2. 实测的单位成本（4 核机器，服务端和机器人在同一台）

| 指标 | 实测值 | 来源 |
|---|---|---|
| 每人下行 | 高档约 19–25 KB/s，低档约 11 KB/s | benchmarks.md §3 |
| 网关 CPU | 800 人 / 27 KB/s 时空闲 76%，忙的部分主要是内核发包（writev），JS 不到 5% | benchmarks.md §5 |
| 单网关进程 | 1000 人：37% CPU，37.7 MB/s 出口，RTT p50 1 ms | benchmarks.md §1 |
| 模拟 | 每个实体每 tick 约 2.3 µs（演示游戏），20 Hz | benchmarks.md §4 |
| 分区效果 | 4 网关 / 32×32 世界 / 600 人：每个网关入口 1.3 → 0.45 MB/s，分片总出口 5.4 → 1.8 MB/s，735 次跨区切换，0 失步 | 本文 §5 |
| 16 个分片 + 分区 + 负载均衡同时开 | 16 个分片全部就绪，23 次自动搬迁，16 个分片地图版本一致，1024 个区块无一丢失，0 失步 | 本文 §5 |

## 3. 10 万人的推荐配置（推算）

假设：平均每人 20 KB/s（高低档混合），世界 128×128 区块（平均每块约 6 人），平均每块 60 个实体（约 100 万实体），演示游戏的模拟成本。**你的游戏的模拟成本请用 `bench/headless.js` 实测后替换。**

| 层 | 进程数 | 机器（示例） | 依据 |
|---|---|---|---|
| 网关 | 约 50 个进程（每进程约 2000 人，留一倍余量） | 4 台 16 核、10 Gbit/s 网卡（每台约 2.5 万人 ≈ 4 Gbit/s） | 实测每进程 1000 人只用 37% CPU，上限在网卡 |
| 分区 | 4×4 = 16 区，每区 3 个网关起步，按在线人数各自扩缩 | — | 每个网关只吞自己区（约 1/16 世界加边界） |
| 分片 | 64 个（8×8） | 8 台 16 核（每台 8 个分片，每个分片约 1.5 万实体，tick 约 35 ms / 50 ms 预算） | 2.3 µs × 1.5 万 × 20 Hz ≈ 0.7 核 |
| 0 号分片（协调 + 控制面） | 1（和其他分片同类） | 建议放在单独的机器上 | 每秒 64 份负载报告；10 万条玩家名录约 30 MB 内存 |
| 入口 | 云四层负载均衡，或 2–4 台 Caddy | — | 16 Gbit/s TLS |
| 内部网络 | 分片 ↔ 网关之间万兆内网 | — | 有分区时内部流量约为对外流量的 1/10–1/5 |

生成这套部署文件：

```bash
node scripts/gen-cluster.mjs --shards 64 --zones 4x4 --gw-per-zone 3 --lobby 4 --world 128x128 --out deploy/generated
# 单机或 Swarm：
cd deploy/generated && DOMAIN=... CLUSTER_SECRET=... TOKEN_SECRET=... ADMIN_TOKEN=... docker compose up -d
# 多台机器：docker swarm init / join 之后
docker stack deploy -c docker-compose.yml soup
```

生成的 Caddyfile 把 `/z/<n>/*` 路由到第 n 区的网关池，其余请求（网页、`/admin`、大厅 `/ws`）交给大厅网关池。

### 带宽成本（粗略，自行核实报价）

带宽几乎就是全部成本：10 万人 × 20 KB/s ≈ 每小时 7.2 TB 出口。

- **按流量计费的大云**（每 GB 几美分到近 0.1 美元）：大约每小时几百美元。
- **带宽包含在月费里、或不限流量的独立服务器 / VPS 商**：成本主要是机器月租。

降低每人带宽的手段（按效果排序）：
1. 默认缩放更小，或默认使用低频档；
2. 减少视野内实体数（这是游戏设计问题）；
3. 降低网络帧率：分片的 `NET_EVERY=4`（20 Hz 模拟、每 4 个 tick 发一帧，即 5 Hz），同时网关设 `NET_HZ=5`，让客户端的插值时长与之匹配；
4. 降低 `FIELD_NET_RES`、`FIELD_EVERY`。

## 4. 部署要点

- **分区数**：大致让每区的在线人数落在几千到两万之间。人特别多的区，直接加大那个区的网关副本数（例如 `deploy.replicas`）。
- **大厅网关**：只负责网页、后台和把新玩家分到对应的区，2–4 个就够。
- **时钟**：所有机器开 NTP。客户端用分片时钟判断哪条信息更新，几十毫秒的偏差没问题。
- **密钥**：所有进程使用同一组 `CLUSTER_SECRET` / `TOKEN_SECRET`。`TOKEN_SECRET` 必须固定不变，否则玩家会丢失身份。
- **监控**：网关的 `/metrics` 重点看 `clients`、`bytesOutPerSec`、`bytesInPerSec`、`watchedOutsideZone`；分片的 `/metrics` 重点看 `tickMs`、`tidi`、`entities`、`droppedActions`；还有后台 `/admin`。
- **扩容顺序**：先看时间流速（tidi）：低于 100% 就加分片或调负载均衡；再看网关 CPU 和网卡，满了就给该区加网关。

### 内核和系统限制（网关机器、压测机器都要调）

```bash
ulimit -n 1048576                                   # 每个连接占一个文件描述符
sysctl -w net.core.somaxconn=65535
sysctl -w net.ipv4.tcp_max_syn_backlog=65535
sysctl -w net.ipv4.ip_local_port_range="1024 65535"  # 压测机：每个目标 IP:端口最多约 6.4 万个出站连接
sysctl -w net.core.netdev_max_backlog=65535
sysctl -w net.ipv4.tcp_tw_reuse=1
```

压测机器发起 10 万个连接时，单台机器对同一个目标地址最多约 6.4 万个出站端口。所以要么用多台压测机器，要么让压测机器连接多个入口地址。

## 5. 在本机做的缩比实验（实测）

**分区效果。** 8 个分片，32×32 世界，4 个网关，600 个机器人（2 个进程，3% 的机器人全量校验）在整个世界里漂移、操作：

| | 不分区（4 个普通网关） | 分区 2×2（4 个区网关 + 大厅） |
|---|---|---|
| 每个网关观看的区块 | 942–1002（几乎是全世界 1024 块） | 320–342（本区 256 块 + 边界） |
| 每个网关内部入口 | 1281–1399 KB/s | 418–482 KB/s |
| 所有网关入口合计 / 分片出口合计 | 5349 / 5392 KB/s | 1815 / 1844 KB/s |
| 每人下行 | 24.8 KB/s | 25.5 KB/s |
| 跨区切换 | — | 735 次（600 次离开大厅 + 135 次跨区），身份全部保持 |
| 失步 / 未知 id | 0 / 0 | 0 / 0 |

区越多，每个网关吞的世界越小。在 2×2 的小世界里，边界重叠约占 22%；4×4 的大世界里边界占比会更小。

**16 个分片的整体验证。** 16 个分片、2×2 分区、自动负载均衡全部打开，120 个机器人（30% 全量校验）：
- 16 个分片全部启动，23 次自动搬迁，所有分片的地图版本一致，1024 个区块全部有主；
- 0 失步，120 次切换（全部离开大厅）没有丢失任何身份。

复现：

```bash
# 不分区
scripts/dev-bg.sh --shards 8 --gateways 4 --world 32x32
# 分区
scripts/dev-bg.sh --shards 8 --gateways 1 --zones 2x2 --zone-host 127.0.0.1 --world 32x32
node bench/bots.js --url ws://127.0.0.1:8080/ws --n 300 --duration 70 --decode 0.03
curl localhost:8081/metrics    # 每个区网关的 bytesInPerSec / watchedOutsideZone
```

## 6. 上线前的 10 万人压测流程

1. 按第 3 节部署好集群。
2. 准备约 25 台压测机，每台 8 核，每台跑 8 个进程、每个进程 500 个机器人：25 × 8 × 500 = 10 万。
   - 每台压测机先做好第 4 节的系统调优；
   - 每台都 `git clone` 本仓库并 `npm install`。
3. 运行：
   ```bash
   HOSTS="压测机1 压测机2 ..." TARGET=wss://你的域名/ws PER_HOST=8 BOTS=500 DURATION=1800 \
   EXTRA="--decode 0.005 --act 0.2 --lo 0.3" ./scripts/bots-fleet.sh
   ```
   - `--decode 0.005` 表示 0.5% 的机器人全量校验协议，结果必须是 0 失步；
   - 机器人会自动经过大厅分到各区，并随镜头漂移跨区切换。
4. 压测期间盯住这些指标：`/admin`、各网关和分片的 `/metrics`、机器人报告的 RTT p95。
5. 通过标准（建议）：
   - RTT p95 < 150 ms；
   - 时间流速 ≥ 95%；
   - 0 失步，`identityLost` = 0；
   - 网关 CPU < 70%，网卡 < 70%。

逐步加压（1 万 → 3 万 → 6 万 → 10 万），每一档都记下单位成本，和第 2 节的数字对比。
