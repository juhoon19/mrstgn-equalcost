# 压测记录

环境：一台 4 核云容器，**分片、网关和压测机器人全部挤在同一台机器上**。真实部署中机器人在别处，服务器数字只会更好。

机器人（`bench/bots.js`）行为：视口 900×520 世界单位缓慢漂移（相当于 1800×1040 屏幕、2 倍缩放），光标 5 次/秒，工具 0.2 次/秒，偶尔聊天，每 2 秒 ping。一部分机器人完整解码快照流，统计协议错误：

- `unknownIds`：增量里出现本流不认识的 id（真正的失步）
- `dupAdds`：重复新增
- `gaps`：帧号跳跃（只在背压丢帧后出现，之后从关键帧恢复）

| | 合并前 | 合并后 |
|---|---|---|
| 成功连接 | 660 / 1000（其余卡在握手） | **1000 / 1000** |
| 网关 CPU | 90% | **37%** |
| 网关出口 | 11.3 MB/s | **37.7 MB/s** |
| 网关发送消息数 | 87 000 /s | 13 700 /s |
| RTT p50 / p95 / p99 | 614 / 2104 / 2622 ms | **1 / 15 / 16 ms** |
| unknownIds / dupAdds | 0 / 0 | 0 / 0 |

## 2. 横向扩展（2 网关，2 分片，4 个机器人进程共 2000 人）

## 3. 带宽优化历程（每人，~450 实体在视野内）

| 步骤 | KB/s |
|---|---|
| 初版：移动记录每实体 ~8 字节，化学场 16×16、2Hz（场占 46%） | 63 |
| 移动记录 id 差分 + 标志位、半径/等级仅变化时发送、位置 1/8 量化；化学场下采样 8×8、1Hz（两项一起测） | **19** |

之后又把纯光标更新降到 5Hz、概览降到每 2 秒一次（未单独测量收益）。

**低频档**（缩小视图用，同样视口，40 个全解码机器人，不播种）：

| 档位 | 每人 KB/s | 其中实体 |
|---|---|---|
| 高档 10 Hz | 19.4 | 13.3 |
| 低档 2.5 Hz | **11.1** | **5.2** |

低档里化学场和概览成了大头（合计约 50%），可以按需再降。

当前字节构成（密集场景）：实体 ~64%，光标/聊天/特效 ~20%（机器人光标很多），化学场 ~10%，概览 ~5%。

## 4. 模拟性能（`bench/headless.js`，单分片 12×12 区块，约 2800 个生物）

| 版本 | ms/tick |
|---|---|
| 初版 | 12.45 |
| 场扩散改为带边界环的模板 + 光照缓存 + 化学每 2 tick 一步 | 6.90 |
| 神经网络/感知去掉每次分配 | **6.35**（≈ 2.3 µs / 生物 / tick） |

优化前后同一随机种子下种群曲线完全一致（逐位相同的生物数），说明优化没有改变行为。

## 5. 网关 CPU 剖析（800 人，单网关进程）

`node --cpu-prof` 60 秒：空闲 75.8%，`writev`（内核发包）12.5%，处理分片帧 2.5%，GC 1.6%，处理客户端输入 0.8%，打包 0.4%。结论：网关的上限是网卡带宽和系统调用，不是 JS；每人 27 KB/s 时 800 人 ≈ 22 MB/s。

## 6. 容器化部署验证

`deploy/docker-compose.yml`：4 个分片容器（2×2 分区，覆盖角落对角交接）+ 网关容器，全部通过 Docker 服务名互联。14 个全解码机器人 40 秒：0 失步，RTT p50 1 ms。（沙箱无法访问 Docker Hub，测试时基础镜像用本机 Node 二进制手工导入；正式构建用 Dockerfile 里的 `node:22-alpine`。）

## 7. 动态负载均衡（热点）

4 个分片（2×2），16×16 世界，150 个机器人全部挤在右下象限（3 号分片），每人每秒 3 次操作（投营养、播种、搅动），`HOT_MS=8`。每 15 秒采样各分片 tick 耗时（ms）/ 持有区块数：

| 时间 | 均衡关闭：s0 / s1 / s2 / s3 | 均衡开启：s0 / s1 / s2 / s3 | 搬迁次数 |
|---|---|---|---|
| 30 s | 3.5 / 3.4 / 3.2 / **13.5** | 4.1 / 6.9 / 4.2 / 14.0（55 块） | 9 |
| 60 s | 4.4 / 4.0 / 4.0 / **28.4** | 4.7 / 11.2 / 10.3 / 18.4（33 块） | 31 |
| 90 s | 4.2 / 4.3 / 4.7 / **29.4** | 7.4 / 13.9 / 13.7 / 16.6（27 块） | 58 |
| 120 s | 5.5 / 6.3 / 7.0 / **34.9** | 12.5 / 15.1 / 15.0 / 17.2 | 76 |
| 150 s | — | 14.7 / 20.0 / 21.7 / 21.4（s0 持有 108 块） | 81 |

- 关闭时热点分片一路涨到 35ms 以上，另外三个闲在 4–7ms。
- 开启后负载先分给两个接壤的分片，再向外扩散到对角的 0 号分片，最后四个分片各 15–22ms；接近平衡后搬迁自动变慢、停止。
- 81 次实时搬迁期间 10% 的机器人全量校验快照：**0 失步、0 未知 id**。
- 调参过程中发现并修复了两个问题：启动初期的噪声导致来回倒区块（加了平滑、预热、持续过热和单块冷却），以及只看最热分片导致负载无法向外扩散（改为按负载依次尝试）。

## 8. 账号 / 交易 / 社交层（`bench/meta-load.js`）

配置：1 分片、2 网关、2 个 meta 副本、PostgreSQL 16，全部和机器人一起挤在同一台 4 核机器上。每个机器人先注册账号，然后用会话 token 重连，和相邻机器人互加好友，之后每秒发 2 次调用。调用组合：30% 私信，15% 查钱包，15% 浏览市场，10% 好友列表，10% 未读数，其余是聊天记录、交易列表、查人、好友申请。

| 并发账号 | 注册耗时 | 吞吐 | 实时推送 | 延迟 p50 / p90 / p99 / 最大 |
|---|---|---|---|---|
| 500 | 9.0 s | 968 次/秒 | 18 642 条 | 2.1 / 5.0 / 16.3 / 220 ms |
| 1500 | 25.4 s | 2898 次/秒 | 56 450 条 | 13.3 / 43.3 / 94.9 / 174 ms |

返回的错误都是预期内的：`RATE` 是每人每分钟 20 条私信的限速在起作用，`BAD_ARG` 是机器人随机挑中自己发好友申请。注册慢是故意的：scrypt 每次哈希约 50 ms CPU，用来拖慢暴力破解。

```bash
DATABASE_URL=postgres://evo:evo@127.0.0.1/evo MAX_PER_IP=100000 REGISTER_PER_IP_HOUR=1000000 \
  node src/launch.js --shards 1 --gateways 2 --meta 2 --port 8095 --world 8x8
node bench/meta-load.js --url ws://127.0.0.1:8095/ws --clients 1500 --seconds 30 --rate 2
```

## 9. 性能优化（先剖析定位，再改；改前改后在同一台 4 核机器上测）

| 层 | 瓶颈（CPU 剖析找到的） | 改法 | 结果 |
|---|---|---|---|
| 分片模拟 | 空间索引是按网格键查的 `Map`：感知半径 60 时每个生物每次查询要查约 25 次哈希；化学场每读一次也查一次 `Map` | 每个 tick 用计数排序建一张稠密网格数组（格内顺序不变），化学场用按区块编号索引的数组 | `bench/headless.js` 4 分片 16×16、第 60 秒（4819 个生物）：每 tick 4.43/3.70/4.14/5.79 → 2.47/2.09/2.32/3.21 ms，**约 1.8 倍**。每次采样的生物数、能量、营养、迁移数**逐位相同**（模拟结果没变） |
| 账号服务 | 约 28% CPU 花在套接字写入上：每个回复/推送单独一帧，每条私信规则单独一次数据库往返 | 同一轮事件循环里的回复、推送、请求合并成一帧（双向，保持顺序）；私信规则检查从 4 次查询合并成 1 次；账号信息缓存 5 秒（本副本写入立即失效，处罚推送到主副本时失效） | 1500 账号、每秒 3000 次请求：p50/p90/p99 **10.1/35.6/91.5 → 6.4/16.5/36.2 ms**；饱和吞吐 3715 → 4258 次/秒 |
| 网关 | — | 没改：剖析显示 64% 空闲，忙的部分主要是内核发包（writev 20%），JS 约 10% | 1000 个机器人：出口 29.6 MB/s，RTT p50 1 ms，0 失步 |
| 浏览器 | 放大时化学场纹理用 `imageSmoothingQuality = 'high'`（双三次）放大，软件渲染下每帧 66 ms；概览图和小地图每帧重画几千个小方块 | 改成 `'low'`（双线性，化学场本来就是模糊的，截图对比几乎看不出差别）；概览图每次更新时画一次到离屏小图，每帧只缩放贴图 | 无 GPU 的 Chromium、1600×1000 放大视角：**66.6 ms → 16.7 ms 一帧（15 → 60 帧，受刷新率限制）**；概览图/小地图的绘制开销从每帧约 7% 降到可以忽略 |

顺带修掉的：端到端精确度测试偶发失败的根本原因（分片在两个 tick 之间收进迁移来的生物，测试恰好在这时暂停，生物在服务器上但还没来得及发给客户端；现在测试在 tick 边界暂停）。

## 10. 混沌测试：1000 个不同行为的玩家 + 故障注入（`bench/soak.js`）

完整集群（2 分片、2 个大厅网关 + 2 个分区网关、2 个账号服务副本、PostgreSQL）跑在一台 4 核机器上，1000 个机器人同时在线 180 秒：

| 类型 | 人数 | 做什么 |
|---|---|---|
| 游客 | 200 | 不登录，到处看、用工具、聊天、调用需要登录的接口 |
| 玩家 | 250 | 注册（含工作量证明）、播种、收集自己的生物、放生、挂单、抢购 |
| 交易者 | 150 | 和别人开交易、加物品和钱、按版本确认、还价、取消，抢最新的挂单 |
| 社交 | 200 | 加好友、接受申请、私信、看未读、改隐私、删好友 |
| 捣乱 | 100 | 发链接和联系方式、刷屏、私信陌生人、举报、拉黑 |
| 混沌 | 100 | 坏 JSON、坏二进制帧、调用内部/管理接口、荒唐参数、同一账号开第二个页面、直接跳到别的分区网关、请求发到一半挂断、退出所有设备再登录、超速连发 |

外加一个管理员每 5 秒禁言/解禁/封号。第 90 秒 `kill -9` 一个账号服务副本，第 115 秒 `kill -9` 一个分片（都由启动器自动拉起）。

结束后自动检查：所有余额之和为 0、没有负余额、每个账户余额等于账本流水、托管锁和挂单一致、每件物品的主人等于它最后一条流转记录、收集日上限、奖励上限、被封账号没有会话、拉黑的人不是好友、500 多个客户端世界副本没有未知实体和重复实体、服务器日志没有报错。

**测出来并修掉的问题：**

1. 私信接口收到非数字的收件人（如数组）时把 `NaN` 传进了数据库，返回“服务器错误”。现在先校验；数据库的“数据格式错误”一律当作参数错误返回。
2. 账号服务退出时先关了数据库连接池，随后上千个连接断开时的离线通知全部报错。现在先停止接活、等进行中的请求做完，再关数据库。
3. 账号服务副本被杀时，发给它的请求要等满 8 秒超时。现在连接一断就立即失败（几毫秒），客户端马上收到“暂时不可用”。
4. **分片崩溃恢复后会出现同一个生物的两个副本**（快照之后越过边界的生物被“复活”），偶发导致客户端收到重复实体。新增确定性测试 `test/crash.test.js`（修前 3/3 失败、修后 3/3 通过），修法见 architecture.md。修复后的两次混沌测试里，恢复的分片分别找出并删除了 19 和 29 个复活副本。

**修复后的两次完整运行**：每次约 12 万次调用、800 个账号、约 2000 笔市场成交、400 多笔交易、1300 多次放生、3000 多次奖励发放；0 个异常，0 个服务器报错，所有数据库不变量成立，521 个世界副本 0 不一致。

```bash
DATABASE_URL=postgres://… ADMIN_TOKEN=x MAX_PER_IP=100000 REGISTER_PER_IP_HOUR=1000000 POW_BITS=8 \
  node src/launch.js --shards 2 --gateways 2 --meta 2 --zones 2x1 --port 8080 --world 16x16
node bench/soak.js --url ws://127.0.0.1:8080/ws --n 1000 --seconds 180 --admin-token x --db postgres://…
```
